Introducing PIM.

A proximity-first mesh network daemon that routes IP traffic hop-by-hop through nearby peers until it reaches a node with internet access.

  • Any device runs as a client, relay, or gateway
  • Peers discover each other automatically — no manual config
  • Any node with internet shares it with the whole mesh via NAT
  • No cloud, no central server, no single point of failure
  • Built in Rust — memory-safe, high-performance, production-grade
  • Runs on Linux and macOS today

Proximity discovery.

Nodes find each other automatically. All three mechanisms run in parallel and are fully additive — once a peer is found, the same TCP session and handshake path takes over.

📡

LAN / UDP Broadcast

Nodes send compact UDP advertisement packets on the local network. Any node that hears one initiates a TCP session automatically.

infrastructure required
🔗

Wi-Fi Direct (P2P)

Drives wpa_supplicant's P2P subsystem. Discovers nearby devices, negotiates GO/GC group formation and DHCP — no access point needed.

no infrastructure
🦷

Bluetooth PAN

Uses bluetoothctl and BlueZ to scan, pair, and establish PAN/NAP links. Learns peer IPs from the PAN neighbor table.

no infrastructure

▸ If the same peer is reachable via multiple mechanisms, duplicate session attempts collapse onto the existing connection — discovery is additive, never duplicated.

$ pim route on && pim route status

Gateway & routing.

  • Any node can be a gateway. If a node has internet, it can share it with the entire mesh via NAT — no special hardware.
  • Route on / off. Clients opt in with pim route on. The daemon injects a default route through the TUN interface on the host.
  • Automatic selection. The routing layer picks the best available gateway. If it disappears, traffic re-routes through the next one.
  • Multi-gateway meshes. Multiple gateways coexist. Tested in Docker with up to four simultaneous gateways.
  • TTL-bounded forwarding. Each MeshDataFrame carries a TTL field that decrements at every hop — loops are impossible by design.

Wire protocol.

TransportFrame — every peer message
magic: u16 2 B 0x504D — "PM" sentinel
version: u8 1 B protocol version
frame_type: u8 1 B Handshake · Data · RouteUpdate · Fragment…
length: u32 4 B payload length in bytes
nonce: [u8;12] 12 B AES-GCM nonce
payload: [u8] N B encrypted, variable length
tag: [u8;16] 16 B AES-GCM authentication tag
MeshDataFrame payload — IP packet carrier
src_id: [u8;16] 16 B originating node identity
dst_id: [u8;16] 16 B destination node or gateway ID
session_id: u32 4 B request / response tracking
ttl: u8 1 B decremented at each hop
flags: u8 1 B fragment, more-fragments, etc.
payload: [u8] N B E2E encrypted IP packet

AES-GCM — authenticated encryption

  • Every frame authenticated: no unauthenticated bytes reach the application
  • 12-byte random nonce per frame prevents replay attacks
  • 16-byte auth tag — forgery detected before decryption

Zero-allocation hot path

Payload encryption happens in-place. No buffer copies on the frame encode / decode path — optimised for high-throughput relay nodes.

Fragmentation

Frames that exceed transport MTU are split via the 0x06 Fragment frame type and reassembled at the destination — transparent to the IP layer.

$ pim inspect --layer stack

Architecture stack.

  • Discovery layer — finds peers via LAN UDP, Wi-Fi Direct, or Bluetooth. Emits a SocketAddr to the transport layer.
  • Transport layer — authenticates via NodeId handshake and establishes persistent TCP sessions with discovered peers.
  • Crypto + Protocol — AES-GCM encrypts each frame in-place. Frames are length-delimited, versioned, and typed.
  • Routing — maintains the mesh routing table; selects next-hop per destination; TTL guards against loops.
  • TUN interface — presents the mesh as a virtual NIC to the host OS. The host routes traffic to it transparently — no app changes needed.
